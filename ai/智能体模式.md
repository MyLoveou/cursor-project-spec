# 智能体常见模式（通用）

> 与 [Agent执行规范](./Agent执行规范.md)、`.cursor/skills/` 配合使用  
> 目标：把路由、编排、并行、eval、handoff 等模式写成可检索对照表

---

## 1. 模式速查

| 模式 | 含义 | 本库落地 | 触发 / 入口 |
|------|------|----------|-------------|
| **路由（Routing）** | 按消息、路径、阶段选 Skill 或子代理 | `workflow-triggers` Rule + Skill | 不确定工作流 → 读 `workflow-triggers` |
| **工作流剧本** | 需求/设计/开发/交付 + **智能体模式对照** | `workflow-playbooks` + `workflows/` + `agent-patterns.md` | 「按需求工作流」等 |
| **顺序编排** | 固定门禁链：范围 → **需求定稿** → 计划 → 实现 → 审查 → 交付 | `scope-check` → `requirements-refinement` → `plan-workflow` → `implement-feature` → … | 新功能、新 API |
| **需求沉淀** | 多轮迭代文档，定稿后再编码 | `requirements-refinement` | 提需求、需求不完整 |
| **委派（Delegation）** | 按改动类型交给 specialist | `build-fix`、`code-review-gate`、`plan-workflow` 委派表 | 构建失败、审查、规划 |
| **Eval 循环** | 先定义 pass/fail，再实现，再回归 | `eval-harness` + `verification-gate` | 新功能、大改、eval |
| **Handoff** | 跨会话状态与续作步骤 | `dynamic-workflow-mode` | handoff、跨会话、多 PR 续作 |
| **并行化** | 只读 lane 并行；写 lane 隔离后并行 | `parallel-execution` Skill | 并行、加快、多 lane、worktree |
| **Harness 构建** | Rules/Skills/Agents/Hooks 分层 | `agent-harness-construction` | 改 `.cursor/**` |
| **人类确认门禁** | 计划 / 拆 PR / **需求定稿** 须用户确认 | `requirements-refinement`、`plan-workflow`、`split-prs` | 提需求、规划、拆 PR |
| **错误恢复** | 403、Flyway、构建失败有固定路径 | `local-dev`、`build-fix`、`agent-harness-construction` | 联调失败、构建失败 |
| **模型路由** | 按任务复杂度选模型 / 子代理档 | `ai-execution.mdc` 摘要；详表见 §3 | 大架构 vs 小改 |

**反模式（全局）**：

- 多 Agent 无 ownership 改同一文件
- 未 `scope-check` 直接写代码
- **需求未定稿**就 `implement-feature`（新能力）
- 写 lane 并行导致冲突编辑
- 跳过 `verification-gate` 声称完成
- Rule 内联整份设计文档（应引用路径）

## 2. 路由三层

```
用户消息 / 路径 / 阶段
    → workflow-triggers（选 Skill）
    → Skill 内委派表（选 @子代理 或 Task）
    → Rule globs（选栈规范：backend / frontend / docs）
```

| 层 | 文件 | 职责 |
|----|------|------|
| 消息路由 | `.cursor/rules/workflow-triggers.mdc` | alwaysApply，**极简**；详表在 Skill |
| 触发表详表 | `.cursor/skills/workflow-triggers/SKILL.md` | **唯一详表**（维护时只改此处） |
| Skill 触发词 | 各 `SKILL.md` 的 `description` | 语义匹配 |
| 路径路由 | `backend-spring.mdc`、`frontend-react.mdc` 等 | globs |

DAILY（项目 `.cursor/skills/`）与 LIBRARY（`~/.cursor/skills/`）选型见 `ecc-manifest.md`。

## 3. 模型与子代理路由（摘要）

| 任务类型 | 建议 | 说明 |
|----------|------|------|
| 分类、窄改、样板 | 轻量模型 / 主 Agent 直做 | 不升格除非失败 |
| 实现、重构、多文件 | 默认实现档 | `implement-feature`、`*-dev` |
| 架构、根因、多 invariant | 高推理档 | `@architect`、`@code-architect` |
| 只读探索 | `explore` / `@code-explorer` | 可与其他只读 lane 并行 |
| 构建修复 | `*-build-resolver` | 先后端再前端（有依赖时） |

**Escalation**：低档失败且原因为推理缺口（非权限/环境）→ 升一档；禁止为「更快」跳过 scope 或 eval。

## 4. 编排 vs 并行

### 4.1 默认：顺序编排（含需求门禁）

全栈新能力默认 **串行**，因存在硬依赖：

```
scope-check → requirements-refinement（多轮，仅文档，已定稿）
  → plan-workflow → migration → 后端 API → 前端 → docs → review → verify
```

### 4.2 何时并行

读 `parallel-execution` Skill。简表：

| Lane | 可并行？ | 条件 |
|------|----------|------|
| 仓库 Grep / Read / git status | ✅ | 只读 |
| 多目录探索 | ✅ | 只读，无写 |
| 后端 vs 前端实现 | ⚠️ | 契约已定；写表面不重叠；migration 已合并或可 mock |
| 双 reviewer | ✅ | 改完各自栈后 |
| 同文件双 Agent 写 | ❌ | 必须串行或单 ownership |
| migration + 依赖该表的前端 | ❌ | migration 必须先 |

大任务在 `plan-workflow` 输出中应标 **Lane Matrix**（见 `parallel-execution`）。

## 5. Eval 与 Handoff

| 阶段 | 文档 / Skill |
|------|----------------|
| 功能级标准（写在前） | `eval-harness`、`.cursor/evals/<feature>.md` |
| 交付级 DoD（写在后） | `verification-gate`、`验证门禁-DoD.md` |
| 跨会话 | `dynamic-workflow-mode`、`*-handoff.md` |

循环：`Define → Implement → Evaluate → Report → verification-gate`
