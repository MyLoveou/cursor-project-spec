# 文档维护（通用）

> 从多项目 `docs-maintenance` 规则抽离；项目可扩展目录名

---

## 1. 推荐 docs 结构

```
docs/
├── requirements/     # 需求、路线图、阻塞清单
│   └── features/     # 单功能需求包（多轮沉淀，定稿后实现）
├── design/           # 架构、API、数据模型
│   └── adr/          # 架构决策记录
├── product/          # 能力边界 / capability
├── standards/        # 编码规范（人类可读）
└── dev-*.md          # 本地联调、测试账号（勿硬编码会变的 ID）
```

---

## 2. 文首元数据

每篇文档顶部建议包含：

- **状态**：草案 / 评审中 / 已定稿
- **最后更新日期**
- **关联文档**链接
- （可选）机器副本路径：`.cursor/rules/xxx.mdc`

---

## 3. 何时必须同步文档

| 代码变更 | 应更新 |
|----------|--------|
| 新/改 REST 路径、请求响应 | `design/03-API设计.md`（或项目 API 文档） |
| 新/改表、实体字段 | `design/06-总数据模型.md` + Flyway migration |
| 架构抉择 | 新建 `design/adr/NNN-标题.md` |
| 交付范围 / Phase | `product/capability.md`、`requirements/路线图.md` |
| 新功能需求包 | `requirements/features/<id>.md`（`requirements-refinement`） |
| 阻塞项关闭 | 阻塞清单状态 → CLOSED |

**原则**：未更新文档就不改对外 API 契约。

### 需求先行（新能力）

1. 在 `requirements/features/` 创建需求包（模板见 `{SPEC_ROOT}/.cursor/templates/docs-requirements-feature.md.template`）
2. 状态：`草案` → `评审中` → `已定稿`（仅已定稿可编码）
3. 定稿后同步 `design/` 下 API、数据模型；流程见 Skill `requirements-refinement`

---

## 4. 编号与修订

- 需求/设计文件可用 `01-`、`02-` 前缀排序
- 重大修改可在文末加「修订记录」表

---

## 5. 禁止

- 未经要求批量重写 README
- 在文档中硬编码会变的测试 ID/token（指向 `dev-测试账号.md`）
- 文档与 `.cursor/rules` 长期不一致（改一处应同步另一处）

---

## 6. 与通用规范库的关系

- **通用**编码/API/Agent 约定 → 规范库根（`{SPEC_ROOT}` 或本库克隆路径）
- **项目专属** Phase、领域术语 → 本项目 `docs/standards/`
