# 企业认证 · 知识发现 / 决断 / 入库

> **发现（开放）→ 上报 → 人决断 → 写入知识表。**  
> 表是活档案，不是封闭清单。Rule `domain-enterprise-cert-confirm` 要求主动发现；本 Skill 规定格式与回写。

## 知识表（活文档）

路径（接入后）：`.cursor/domain-packs/enterprise-cert/`  
（规范库：`domains/enterprise-cert/`）

| 表文件 | 写入什么 |
|--------|----------|
| `pending-decisions.md` | **待决断**队列（上报时先写入/更新） |
| `glossary.md` | 已确认**术语** |
| `taboos.md` | 已确认**禁忌**与「必须先问」的稳定项 |
| `business-rules.md` | 已确认**业务规则**（优先级、校验、状态、渠道条件等） |
| `ui-interactions.md` | 已确认**UI/交互**（时机、展示、拦截文案、AB 下差异等） |
| `coding-conventions.md` / `conventions-pending.md` | 工程惯例（由 `codebase-conventions` 维护；与业务表分列） |

种子条目可以很少；随实践增长。实现时**只信任各表中标注「已确认」的行**。

### 与 MCP Knowledge Graph（可选）

跨会话短记忆见 `tooling/mcp-knowledge-graph.md`。  
**人决断后的条目以本表 md 为真源**；可再镜像摘要到 MCP（observation 注明台账路径）。禁止只写 MCP 当已确认。

## 阶段 A · 开放发现

在需求穷尽、摸底、写方案、实现、CR 反馈时都要做。输入：PRD、Figma、口述、代码、CR 意见。

### 扫描问题（引导发现，非勾选完毕即结束）

对每个相关页面/字段/步骤问：

1. 这里有没有**未写进表**的业务约束？
2. 有没有**术语**双方可能理解不一致？
3. 用户从进到出，有哪些**交互分支**（成功/失败/返回/再进/AB off）？
4. 不同**站点/国家/渠道**是否可能不同？证据是什么？
5. 无数据/失败时允许**什么行为**（留空、拦截、禁止兜底）？
6. 是否涉及**改旧 vs 新增**且表中无团队先例？

凡「说不准」或「表中没有已确认结论」→ 记为候选，进入阶段 B。  
**禁止**：只对照旧 T1–T8/Q1–Q8，扫完固定表就宣布无问题。

## 阶段 B · 上报（【知识待决断】）

为每条候选分配临时 ID：`P-<日期>-<序号>`（如 `P-20260727-01`）。

```markdown
【知识待决断】企业认证

| ID | 类别 | 摘要 | 为何不能猜 | 建议入库表 | 未决断前不做 |
|----|------|------|------------|------------|--------------|
| P-… | 业务规则 / 领域知识 / UI交互 / 术语 / 禁忌风险 / 实现取舍 | … | … | business-rules / glossary / ui-interactions / taboos | … |

依据摘录：（PRD 句 / Figma 帧 / 代码路径，可短）

请逐条决断。示例回复：
- `P-… = 确认：无渠道值时国籍留空，禁止用注册地；入库 business-rules + taboos`
- `P-… = 驳回：不在本需求`
- `P-… = 延期：先问产品 @某`
```

同时更新 `pending-decisions.md`（追加/改状态为 `open`）。

有 `open` 项且影响当前切片 → **STOP** 该点实现，可继续无关切片（须声明）。

## 阶段 C · 决断后入库（强制）

用户给出结论后，**立即**改文件（规范库或业务仓 `.cursor/domain-packs/enterprise-cert/`）：

1. 按「建议入库表」追加一行，状态写 **已确认**，带：结论、日期、来源（P-ID / 人）
2. `pending-decisions.md` 对应行 → `closed`，链到入库位置
3. 若否定/不在范围 → pending 标 `rejected`，**不要**当业务规则执行
4. 回复中列出「已写入：文件 + 条目摘要」

### 入库行格式（各表统一风格）

**glossary.md**

```markdown
| 术语 | 含义 | 注意 | 状态 | 来源 |
|------|------|------|------|------|
| … | … | … | 已确认 | P-… / 姓名 / 日期 |
```

**business-rules.md**

```markdown
| ID | 规则 | 适用范围（站点/国家/AB） | 状态 | 来源 |
|----|------|--------------------------|------|------|
| BR-… | … | … | 已确认 | P-… |
```

**ui-interactions.md**

```markdown
| ID | 场景 | 时机/行为 | 状态 | 来源 |
|----|------|-----------|------|------|
| UI-… | 离开再进 | 进页重拉 KYB，与草稿对比… | 已确认 | P-… |
```

**taboos.md**：仅稳定「禁止/必须先问」项；用原有表格追加行，并注来源 P-ID。

## 阶段 D · 与 SDD 的衔接

| 时机 | 动作 |
|------|------|
| SDD 阶段 1 需求穷尽 | 对 PRD/Figma 做一轮发现 → 待决断清零或标延期 |
| 摸底/方案/实现中新发现 | 随时上报；影响方案则走变更单 |
| 用户说「写入表」「沉淀这条」 | 直接阶段 C |
| 口令「知识上报」「决断入库」 | 本 Skill |

## 反模式

- 固定清单扫完 = 发现完毕
- 人已决断但只回「好的」不改 md
- 把 pending 当已确认去写代码
- 入库不写适用范围（导致他站误用）
