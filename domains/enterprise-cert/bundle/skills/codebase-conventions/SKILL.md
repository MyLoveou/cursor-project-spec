# 代码隐性规范提炼（Codebase Conventions）

> 代码里常有「没写成文档、但大家默认这么写」的约定。  
> 本 Skill：**采样证据 →【规范待决断】→ 人确认 → 写入台账**（同构于业务侧 `knowledge-capture`）。  
> **AI 初稿 ≠ 项目规范**；未确认不得当硬约束执行，更不得直接写成 alwaysApply Rule。

## 何时用

- 接手仓库、不知目录/命名/错误处理惯例
- 写方案前要「按现有风格」但说不清风格
- 准备沉淀 `.cursor/rules` 或域包工程约定
- 口令：「提炼规范」「从代码抽约定」「项目惯例」

## 与相近能力的区别

| Skill | 提炼对象 |
|-------|----------|
| **本 Skill** | 编码/工程**隐性规范**（命名、分层、错误、测试、配置方式…） |
| `codebase-inventory` | **功能现状**（入口、API、地区差分、可复用点） |
| `domain-*-knowledge-capture` | **业务规则 / 术语 / UI 交互** |
| `continuous-learning-v2` | 从**会话行为**学 instinct（需 hooks），非主动扫库 |
| `search-first` | 单次「有没有现成实现」，不沉淀规范库 |

可先 inventory 再 conventions；二者证据可互相引用，台账分开。

## 产出位置（活文档）

默认写入业务仓（按项目已有约定调整）：

| 文件 | 内容 |
|------|------|
| `docs/standards/coding-conventions.md` | **已确认**工程规范台账 |
| `docs/standards/conventions-pending.md` | **待决断**队列 |
| 可选 | 确认后由人决定是否再生成/更新 `.cursor/rules/*.mdc`（本 Skill 只给草案，不擅自 alwaysApply） |

域包场景可改为：`.cursor/domain-packs/<id>/coding-conventions.md`（与 business-rules 并列）。

## 流程

### 阶段 A · 采样范围

1. 与用户确认范围：全仓 / 某包 / 某域路径（如企业认证相关目录）
2. 列出采样维度（按需裁剪，**开放列表**，勿当成穷尽）：

| 维度 | 看什么 |
|------|--------|
| 目录与分层 | feature vs type、client/server 边界 |
| 命名 | 文件/组件/函数/API/config key |
| 状态与数据 | store、query、form、DTO 习惯 |
| 错误与边界 | try/catch、错误码、空态、权限失败 |
| 接口调用 | 封装层、是否分地区/站点 |
| 配置与开关 | AB、feature flag、环境变量 |
| 样式/UI 结构 | 组件库、样式方案（若相关） |
| 测试 | 测什么、放哪、命名 |
| 注释与文档 | 何时写注释、文档落点 |

### 阶段 B · 证据采样（必做）

每个候选规范至少：

- **2+ 独立命中**（不同文件），或 1 处但有目录级 README/注释明说
- 路径 + 短摘录/符号名
- 反例（若找到「也有另一种写法」必须记下 — 可能是例外或规范分裂）

输出候选表，**状态一律 `待确认`**：

| ID | 维度 | 候选规范（一句话） | 证据（路径） | 反例/分裂 | 建议强度 |
|----|------|--------------------|--------------|-----------|----------|
| C-… | 命名 | … | … | … | 偏好 / 强制 |

建议强度：

- **强制**：违反即 bug/CR 必改  
- **偏好**：无强理由应遵循  
- **仅观察**：样本不足或严重分裂，只记录不执行  

### 阶段 C ·【规范待决断】

```markdown
【规范待决断】

| ID | 候选 | 建议强度 | 问题（请决断） | 未确认前不做 |
|----|------|----------|----------------|--------------|
| C-… | … | 偏好 | 升为强制？写入 Rule 还是只进台账？ | 不当成硬约束改代码 |

请回复：`C-… = 确认：强制；入库 coding-conventions` / `驳回` / `仅观察`
```

同步写入 `conventions-pending.md`。

### 阶段 D · 入库

人确认后：

1. 追加到 `coding-conventions.md`，状态 **已确认**，带日期与来源 ID  
2. pending → closed  
3. 若用户要求落 Rule：给出 **短 Rule 草案**（门禁句 + 例），经用户同意再写入 `.cursor/rules/`；默认只更新台账  
4. 回复列出「已写入」路径

### 入库行格式

```markdown
| ID | 规范 | 强度 | 适用范围 | 状态 | 证据摘要 | 来源 |
|----|------|------|----------|------|----------|------|
| CV-… | … | 强制/偏好 | 路径或栈 | 已确认 | file1, file2 | C-… |
```

## 门禁

- 未确认的候选 **不得** 当作「项目规范」要求实现必须遵守  
- 样本 &lt; 2 且无文档佐证 → 最多「仅观察」  
- 发现规范分裂 → 上报决断，禁止擅自选一边写进强制  
- 与业务禁忌冲突时：业务/产品裁定优先，工程规范让位并记录  

## 反模式

- 把训练数据里的「最佳实践」写成仓库规范（无本仓证据）  
- 一轮 Grep 就输出长篇 style guide  
- 未决断就生成 alwaysApply Rule  
- 与 `knowledge-capture` 混台：业务规则进 business-rules，工程约定进 coding-conventions
